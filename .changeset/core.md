---
"@vega-ui/core": minor
---

New package `@vega-ui/core` holds the logic of composite widgets, written as one pipeline with no dependency on React or the DOM: `event → normalize → step(state, input) → { state, actions } → output(state) → DOM`. The adapter does the first and the last arrow; everything in between is pure and runs in node.

- `state({ options, owns, internal, observes, collection })` declares the shape of a widget's state. `controlled(fallback, initial)` is a value the parent may control through `x`, `defaultX` and `onChangeX`, with an optional `initial(options)` that starts it from the other options in place of `defaultX`; `internal(fallback)` is a value only the widget and its output see; `matching(part, selector)` is a value the browser owns, like whether a popover is open, that the adapter reads before every dispatch, so the browser wins over the parent and the widget. The shape gives one typed field per value (`shape.active.get(state)`, `shape.active.set(state, key)`), a reader per option (`shape.options.mode`), and `shape.part(select, render)` for the output. Every value takes a name of its own: a name the snapshot or the shape already uses, like `id`, `focused` or `create`, the name of another value, or an option named like an owned value is a type error. A snapshot is plain data: the options, the collection, the `id`, the running timers, whether the widget is focused, the observed values and the owned and internal values; `idOf(state, part, key)` builds an element id
- `source({ key, disabled, label })` turns the items of the options into a collection, reused while the items array is the same: `order`, `index`, `disabled` and `labels` as data, and the functions `collection.next`, `previous`, `first`, `last`, `nearest`, `between`, `selectable` and `findByLabel` over it, all skipping disabled items
- Inputs are values, not strings: `key.arrowDown`, `key.with(key.a, mod.mod)`, `key.printable` for any single character, `nav.forward` / `backward` / `first` / `last` / `pageForward` / `pageBackward` as the logical directions the adapter builds from the arrows, the orientation and the writing direction (`toNav`), plus `nav.up` / `down` in a grid, where the arrows of both axes are directions, `pointer.down` / `press` / `drag` / `dragOver` / `release` / `cancel` / `hover`, `focus.enter` / `move` / `leave`, `text.change`, `browser.toggle` / `cancel` / `close` / `submit` / `reset` / `animationEnd`, `measure.done` for the answer to `act.measure`, `timer(name)` and `command(name)` for an input a framework sends itself, like an imperative `focus(key)`, and `lifecycle.connect` / `lifecycle.options` for the moment the adapter is connected and for a change of a value the parent controls or of an option the shape names in `follows`, like the page a scroller follows, with the names of the changed options in `changed`. A typo is a type error, `input.key` is typed by the key of the collection, and `defineInput(type, name)` declares an input of your own. A pointer or key input carries the item `key` and the named `part` it hit, so a step tells a press on the trigger from a press on an option, `inside` when the event came from a control inside the item, like a button in a grid cell, so a step leaves those to the control, and `content` when the item holds focusable content, so a step sends the focus into it; a `command` carries `keys`, a list of keys, like the cells of a page that scrolled into view
- A step is `(state, input) => handled(next, actions) | keep(next, actions) | stop(next) | undefined`: handled prevents the browser default, keep leaves it, undefined passes the input on. `listening(inputs, step)` declares the inputs a step reads from the browser, the widget collects them as `listens`, and the adapter listens only to the events that give one of them, plus the focus, and delivers a key only when a step declares it or the direction it becomes, reading the writing direction only for a key RTL changes, so a key no step reads stays with the browser; a command, a timer, a lifecycle input or an input of your own needs no declaration. The widget runs its steps in order and the first answer wins. Actions are data the adapter executes after the state is committed: `act.focus(key, preventScroll)`, `focusInside(key, 'first' | 'next' | 'previous')` for the focusable content of an item, `focusPart(part)`, `reveal`, `click`, `timer`, `cancelTimer`, `showPopover`, `hidePopover` and `send(part, input, payload)`, which delivers an input to the widget whose root is that part, so a widget drives a widget inside it, like a calendar focusing the day of its day grid, and `measure({ name, parts, items, rect, scroll, styles, viewport })`, which the adapter runs after the DOM shows the new state, reading every request first and then answering each with a `measure.done` input of plain numbers, so geometry is data a step tests in node. `awaitAnimations(part)` waits for the animations the part runs once the DOM shows the new state, read with `getAnimations()`, and answers with `browser.animationEnd` and the `part`, also at once when none runs, so a closing popover or section is hidden when its animation really ends. An owned field tells whether the parent controls it, `shape.open.controlled(state)`, so a step hides a popover on a close request only when no parent can keep it open. A `browser.toggle` input carries the `part` whose own toggle it is, so a widget tells its popover from one nested inside. The adapter follows `cancel`, `close` and `submit` for a native `<dialog>`: `browser.cancel` and `browser.close` carry their `part`, and `handled` prevents a cancel; `browser.submit` carries the `part` of the form, its method as `to` and the `value` of the submitter. A press on the backdrop of a modal dialog carries `backdrop`. `act.showModal(part)` shows a dialog and answers with `browser.toggle` once it is shown, also in browsers without dialog toggle events, and `act.closeDialog(part, returnValue)` closes it. `awaitAnimations` waits for the animations of the element and its pseudo-elements, like `::backdrop`, not of its children. Actions are typed by the key of the collection: a step is `Step<S, K>`, with `K` the key of the state by default, so a fragment generic over its state still returns actions of its own key
- `defineWidget({ state, step, output, invariants })` keeps the type of `output`, so `widget.output.root` renders the attributes its `shape.part` declares, and `createWidget(widget, options, { id, strict, onRepair, onError, onDispatch })`, where `id` is required and comes from the framework, so the ids of the parts are the same on the server and the client: every dispatch is a transaction, a step that throws leaves the state as it was, each invariant is checked after every commit, from the first snapshot on: one a step breaks while it held throws in strict mode and is repaired otherwise, so a value the parent controls against an invariant blames no later step, one the options break is repaired in strict mode too, without `onChangeX`, and `repair(state, before)` gets the snapshot before the commit, a repair never writes a value the parent controls, `onDispatch` traces every transaction as `{ input, answer, actions, before, after }`, `setOptions` returns the actions of the `lifecycle.options` it dispatches when the parent changes a controlled value, a changed owned value calls its `onChangeX` once and keeps the new value until the next `setOptions` brings the parent's answer, so a controlled value renders once per change, `setOptions` never calls `onChangeX`, and `render(part, key)` returns the previous attributes while the selected inputs of the part are the same
- `setOptions` never calls an `onChangeX`: the parent sets options while it renders, so a step answering `lifecycle.options` follows them with what it shows and never changes an owned value; a strict widget refuses one that does with an error
- Fragments are steps any widget composes: `roving({ active, strategy, hover, page })` moves the active key with the logical directions and on pointer down, under the pointer with `hover`, and by `page` items on PageUp and PageDown, with `focus` or `activedescendant`; `selection({ value, active, anchor, mode, strategy, keys })` follows the APG listbox: a press or one of `keys` (Space by default) toggles, Shift+Arrow moves and toggles, Shift+Space selects from the most recently selected option to the active one, Ctrl+Shift+Home/End selects to the first or last option, Mod+A selects all, and in single mode picking the selected option again changes nothing. The same fragment selects in two dimensions and in ranges: `mode` may be `range`, `extend: 'range'` makes Shift+Arrow extend from the most recently selected key instead of toggling, `selectable`, `compare`, `between`, `resolveRange` and `all` let a grid define its own order and its own cells between two keys, `extension` and `gesture` are fields for the extension in progress and for a pointer drag, and the returned step carries the verbs a widget calls from steps of its own, `isSelected`, `edges`, `toggle`, `extend(from, to)`, `selectAll`, `press` and `drag`; the `grid` fragment is the layout of a grid: `createGridLayout({ positions, flags, isExcluded, compare })` builds the rows, the columns and the collection from the key, row and column of every cell, `gridNeighbor(layout, from, intent, wrap)` finds the cell in a direction (`forward`, `backward`, `up`, `down`, `rowStart`, `rowEnd`, `gridStart`, `gridEnd`, `pageUp`, `pageDown`) with the wrap, and `gridBetween(layout, from, to)` lists the cells between two keys in reading order; `typeahead({ active, typed, strategy, enabled })` finds an option by its typed letters, cycles through the options starting with a repeated letter, keeps the buffer while its timer runs and drops it when the focus leaves
- A part may carry a `live` channel, CSS variables and attributes that change on every frame, like the offset of a drag, and a `props` channel, the properties and methods of the element, like `indeterminate`, or `invalidAs`, the attributes of a native input that would be invalid the same way, which the adapter turns into the message of the browser through `setCustomValidity`, each with a selector of its own, built with `shape.part(select, render)` like the part, so the renderer gets the typed selection. The DOM adapter writes them itself after every dispatch and on `flush`, only when the selection changed, on the elements registered with the part, without a render of the framework; `props` cannot write `value`, `checked`, `open` or `selected`, which the browser and the parent own
- `pointer.enter` and `pointer.leave` arrive once per part or item the pointer crosses, from `pointerover` and `pointerout`, with the `pointerType`, and a leave carries the part the pointer moves to as `to`, so a tooltip stays open while the pointer moves from its trigger onto it and ignores a tap. `act.watchKeys()` and `act.unwatchKeys()` bring the keys pressed anywhere on the page to the steps, like `Escape` for a tooltip opened by hover; a key inside the widget's roots or one another widget handled is not delivered twice. `reading(read, fallback)` observes a value from outside the page with `read(options)` before every dispatch, like whether a group of tooltips is warm, so the step stays pure. The attribute that starts the animations `awaitAnimations` waits for belongs to the `live` channel: a framework may render later than the adapter reads the animations
- The options of a widget are typed: `OptionsOf<typeof shape>` is the declared options plus `x`, `defaultX` and `onChangeX` for every owned value, so a typo in an option, a wrong mode or a callback of another type is a type error at `createWidget`, `simulate` and `useWidget`
- `connect(instance, elements, { onError })` is the DOM adapter: `connection.listen(root)` or the `keydown`, `click`, `pointerdown`, `pointermove`, `focusin`, `focusout`, `input` and `toggle` handlers attached by a framework for the `connection.events` the widget declares. It builds the inputs from events (`keyInput`: `Spacebar` is Space, Ctrl+A on a non-Latin layout is read from `code`, composing keys are skipped), maps the arrows through `aria-orientation` and the writing direction of the root (without `aria-orientation` a `grid` or `treegrid` role is a grid, a `tablist`, `menubar` or `toolbar` is horizontal, as their implicit ARIA orientation), finds the item key through `elements.keyOf`, and yields to the browser inside text entry for caret keys and printable characters and for a key from a control inside an item whose popup is open, `aria-expanded="true"` or an open popover or dialog in the item. The user's handler runs first: an event with `defaultPrevented`, or one an inner widget already handled, is skipped, also when a framework delivers the same event to two handlers or when its target is outside the root in the DOM, and `handled` on keydown and click makes the handler return `true`: the caller prevents the browser default through its own event, `listen` on the native one, so the handlers of a framework above the widget see `defaultPrevented`. Before every dispatch the adapter reads the observed browser values and `focused` and hands them to the widget with the input, so one event is one commit. The orientation and writing direction of the root are read on every key, so a `dir` changed on an ancestor applies at once. A pointer press owns the pointer until release through document listeners, a move of the pressed pointer is `pointer.drag` with its `point` and `pointerType`, and only a widget that declares `pointer.dragOver` gets the key under the moving pointer and pays for the hit test, `buttons === 0` on move counts as a release, a focus moving between two items inside the root is `focus.move`, a focus leaving the root cancels a pointer press, timers fire back as `timer(name)` inputs, `connection.send(input)` dispatches an input without an event and runs its actions, `connection.observe()` reads the observed browser values before a framework calls `setOptions`, so a `lifecycle.options` step sees the browser as it is, an action that throws is reported to `onError` and the others still run, an action that cannot run yet (focusing an element that is not rendered) waits and is retried with `connection.flush()` until it runs, a later focus replaces a waiting one, a waiting action is dropped when its key leaves the collection or the focus leaves the root, while an action for a key the collection never had, like the next page of a virtualized grid, waits for the key to register, a `focus` whose element did not take the focus, like a cell in an `inert` page, keeps waiting and runs once it can, a focus the connection moved itself is not dispatched back, and `disconnect()` removes every listener and timer. The adapter listens to the page, the document, the window and the `ResizeObserver` of the roots, only once a root registers, so a connection made on the server or for a render that never commits, like the first of the two a strict mode runs, touches nothing. `createElements()` is the registry of the roots, the named parts and the items by key that the adapter reads (`rootOf`, `keyOf` and `partOf` an element). `setRoot(element, name)` registers one more root, like a popover content in the top layer apart from its trigger; each root is the part of its name, an event inside any root belongs to the widget, the nearest root gives the key and the direction, a focus moving between two roots stays inside, and an event that bubbles through two roots of one widget is dispatched once. `setItem(key, element, data)` keeps data with the element, `entries()` lists the items in DOM order as `{ key, data }`, without the elements, so a widget's options stay plain data, cached until an item registers or a registered element is added, removed or moved in the root's subtree (a `MutationObserver` on the root follows reorders; a text change does not re-sort), and `version` with `subscribe` let a framework rebuild its collection from the DOM; `within(container)` lists the keys of the items inside an element, like the cells of the page that scrolled into view
- `simulate(widget, options, { orientation, rtl })` from `@vega-ui/core/test` drives a widget in node: `send(key.arrowDown)`, `pressAt(key)`, `type('da')`, `setOptions`, `observe`, with strict invariants, refusing an input from a browser event no step declares, also a form reset, a resize or a selection change the adapter follows on the page itself, or a key no step reads, which the adapter would never deliver
- A drag can take the pointer from the page: `act.claimPointer()` keeps a touch from scrolling the page or the content under it until the release, through a `touchmove` listener on the root that a framework attaches with `passive: false` before any touch starts, as iOS decides at the start of a touch whether a page may hold its scroll and swallows the click that ends the press on the widget, and a press on the page clears it, so a drag that ends without a click does not eat the next tap. The press carries its `time` and whether it is `primary`, and, for a widget that declares `pointer.drag`, whether it pressed `text` and the vertical `scroller` between its target and the root; the drag carries its `time`, the release its `point` and `time`, the cancel only its `time`, since the browser gives it no point. A drag never overtakes the measure its press asked for: the adapter answers it before the first move
- `act.scrub(part, { keyframes, pseudoElement, progress })` seeks one paused animation of a part, created on the first scrub, like the backdrop of a dragged sheet, so a move writes no style the browser recomputes, and `act.stopScrub(part)` cancels it; `act.flushStyles(part)` applies the pending styles and answers with `browser.flushed`, so the next state starts its transitions from the one just written. The measured `viewport` is the layout viewport without scrollbars, with the `keyboardInset` an on-screen keyboard covers
- Scrolling is an input and an action: `scroll.move` on every scroll of a root and `scroll.end` when it stops, from `scrollend` or, where a browser has none, 80 ms after the last scroll, both with the `scroller` box, `layout.resize` when a root changes its size, from a `ResizeObserver` the adapter keeps on every root, also on one registered after connecting, `layout.viewport` when the window or the visual viewport resizes or the visual viewport scrolls, both observed only for a widget that declares them, `pointer.wheel` from a passive `wheel` listener, `pointer.spin` with the wheel `delta` from a `wheel` listener that is not passive, only for a widget that declares it, so a step that answers `handled` keeps the page from scrolling, like a number field stepped by the wheel, and `act.scrollTo(part, options)`, which scrolls the part at once. `act.emit(name, value)` calls the `on<Name>` callback of the options, for an event that is not a value the widget owns
- Text entry is an input and an action: `text.edit` from a cancelable `beforeinput` carries the `field` before the edit, its `value` and `selection`, and the `edit`, the `inputType` and the inserted `data`, also of a paste or a drop, so a step masks the text before the browser changes it; a composition is left to the browser and arrives as `text.change` once it ends. `text.change` and the key inputs from a text field carry the `field` too. `act.setText(part, value, selection?)` writes the text through the native setter, so a framework's `onChange` reports it, dispatches an `input` event the adapter does not hand back, and moves the caret only while the field is focused; `act.commitText(part, value)` also dispatches `change`, like a native picker that commits a value, and `act.commit(part)` dispatches only `change`, like a text field the user edited and left, since the browser does not count a text the adapter writes as an edit of the user. `browser.reset` arrives from a form reset once the browser restored the defaults, for a widget that declares it and holds a form control. `browser.load` and `browser.error` arrive from the `load` and `error` of a root, like an image. `text.select` arrives with the `field` when the selection of a focused text field of the widget changes or the field takes the focus, from the `selectionchange` of the document, and once the pointer is released while it selects, so a step that keeps the caret out of a prefix does not fight a drag. A text field that is the root itself hands the caret keys and the typed characters to the widget, which leaves to the browser the ones it does not answer, while a text field inside an item still yields them. A text field root without `aria-orientation` is horizontal, so ArrowUp and ArrowDown stay keys
