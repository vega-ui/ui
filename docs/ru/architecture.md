# Архитектура

VegaUI — воркспейс `pnpm` под управлением Turborepo. Главная архитектурная идея — не само дерево папок, а направление зависимостей между пакетами.

## Слои системы

Репозиторий построен как многослойный стек дизайн-системы:

1. `packages/tokens`
   Исходные дизайн-токены: цвета, отступы, скругления, тени, типографика и слои.
2. `packages/theme`
   Семантические переменные темы поверх токенов. Здесь определены `.light` и `.dark`.
3. `packages/ui`
   React-компоненты и CSS-модули компонентов, которые используют семантику темы.
4. `docs/` и Storybook
   Документация для людей, примеры и рекомендации по интеграции поверх опубликованного API.

Читайте этот стек слева направо:

`tokens -> theme -> ui -> stories/tests/docs`

## Пакеты воркспейса

- `packages/ui`: основной React-пакет, публикуется как `@vega-ui/react`
- `packages/theme`: глобальный семантический слой темы, публикуется как `@vega-ui/theme-core`
- `packages/tokens`: исходные дизайн-токены, публикуются как `@vega-ui/tokens-core`
- `packages/icons`: ассеты и экспорты иконок
- `packages/core`: логика составных виджетов без фреймворка, публикуется как `@vega-ui/core`: конвейер `состояние → шаг → действия → вывод`, фрагменты `roving`, `selection`, `typeahead` и `grid` и DOM-адаптер (см. [Виджеты](#виджеты)); в `@vega-ui/core/test` лежит `simulate` для node-тестов
- `packages/widgets`: виджеты компонентов, публикуется как `@vega-ui/widgets` с отдельной точкой входа на каждый виджет, например `@vega-ui/widgets/select`; зависит от `core`, `i18n` и `utils` и никогда от React, поэтому его может переиспользовать адаптер для другого фреймворка
- `packages/hooks`: общие технические хуки — контролируемое состояние, отслеживание размеров
- `packages/utils`: низкоуровневые утилиты — слияние пропсов, рефы, даты и небольшие помощники для данных
- `packages/i18n`: независимые от фреймворка адаптеры календарных систем, помощники для локалей и форматирования, календарно-зависимые помощники для ISO-дат и адаптер телефонной нумерации на `libphonenumber-js`, публикуется как `@vega-ui/i18n` (см. [Даты и календарные системы](./i18n.md))

## Модель зависимостей

Важное направление зависимостей:

- `ui` зависит от `core`, `widgets`, `hooks`, `i18n`, `icons` и `utils`; React-адаптер виджета (`useWidget`, `useOutput`, `useSnapshot`, `useItem`) и `createContext` живут во внутренних модулях `ui`
- `hooks` зависит от `core`, а `core` не зависит ни от чего
- `theme` зависит от `tokens`
- компоненты в `ui` стилизуются через семантические переменные из `theme`

Это значит:

- изменения токенов затрагивают всю систему стилей
- изменения темы переназначают семантику, не переписывая каждый компонент
- локальные CSS-переменные компонента должны оставаться локальными и не подменять слой темы

## Структура UI-пакета

Большинство компонентов в `packages/ui/src/<Component>/` следуют повторяемой структуре:

- `Component.tsx`: публичная реализация компонента
- `types.ts`: экспортируемые типы и объединения, когда они нужны
- `index.ts`: публичные экспорты для точки входа пакета
- `style.module.css`: локальные стили компонента
- `components/`: экспортируемые дочерние части составных компонентов
- `contexts/`: общий локальный контекст для состояния составного компонента
- `__tests__/*.browser.test.tsx`: браузерные тесты взаимодействия
- `*.stories.tsx`: примеры использования в виде историй

## Виджеты

Компоненты, у которых поведения больше, чем у нативного элемента, — `Listbox`, `Select`, `Grid`, пикеры и `Calendar` на нём — держат это поведение в виджете: обычный TypeScript в `packages/widgets/src/<component>/widget.ts` (или в `packages/widgets/src/<segment>`, если его делят два виджета), который не импортирует ни React, ни DOM. React-компонент — тонкий адаптер вокруг него. У компонентов, близких к нативному элементу (`Button`, `Switch`), виджета нет; у `Checkbox` он есть только ради свойства `indeterminate`, которое его input не принимает атрибутом.

### Один конвейер

```
событие → нормализация → шаг(состояние, поступление) → { состояние, действия } → вывод(состояние) → DOM
```

Первую и последнюю стрелку делает адаптер. Всё между ними — простые данные и чистые функции, поэтому виджет работает и тестируется в node. Пять понятий, все в `@vega-ui/core`:

- **Состояние**: неизменяемый снимок из простых данных, рядом с options в том виде, как их дал родитель, вместе с колбэками. Его объявляет `state({ options, owns, follows, internal, observes, collection })`. `follows` называет опции, изменение которых приходит как `lifecycle.options` наравне со значениями, которыми управляет родитель, например страница, за которой следует скроллер. `controlled(fallback, initial)` — значение, которым родитель может управлять через `x`, `defaultX` и `onChangeX`, а `initial(options)`, если задан, вычисляет его начало из options вместо `defaultX`, как страну номера по умолчанию; `internal(fallback)` — значение, которое видят только виджет и его вывод; `matching(part, selector)` — значение, которым владеет браузер, например открыт ли поповер: адаптер читает его перед каждым dispatch; `reading(read, fallback)` — значение извне страницы, которое адаптер читает так же, например прогрета ли группа подсказок; `collection` — упорядоченные ключи с флагами, которые `source(spec)` или раскладка строят один раз на массив элементов. В снимке есть также `id` виджета, идущие таймеры и `focused`; значение с таким же именем, с именем метода формы или другого значения — ошибка типа. Производное не хранится: `idOf(state, part, key)`, `tabStop(state)` и подобное — функции от снимка, мемоизированные по идентичности.
- **Поступление**: значение с полезной нагрузкой, не строка. `key.arrowDown`, `key.with(key.a, mod.mod)`, `nav.forward` (адаптер превращает стрелки в логические направления по ориентации и направлению письма, то есть по атрибуту `dir` корня или предка), `nav.up` / `down`, `pointer.down` / `press` / `drag` / `dragOver` / `release` / `cancel` / `hover` / `enter` / `leave` / `wheel` / `spin`, `scroll.move` / `end`, `layout.resize` / `viewport`, `focus.enter` / `move` / `leave`, `text.edit` / `change` / `select`, `browser.toggle` / `reset` / `load` / `error` / `cancel` / `close` / `submit` / `animationEnd` / `flushed`, `measure.done`, `timer(name)`, `command(name)` для поступления, которое фреймворк посылает сам, `lifecycle.connect` и `lifecycle.options`. Опечатка не компилируется, а `input.key` типизирован ключом коллекции.
- **Шаг**: `(state, input) → handled(next, actions) | keep(next, actions) | stop(next) | undefined`. `handled` отменяет действие браузера, `keep` оставляет, `undefined` передаёт поступление следующему шагу, а затем виджету выше. Виджет перечисляет шаги по порядку, первый ответ побеждает.
- **Действие**: данные, которые адаптер исполняет после коммита: `act.focus(key)`, `focusInside(key, at)`, `focusPart(name)`, `reveal(key)`, `click(key)`, `timer(name, ms)`, `cancelTimer(name)`, `showPopover(part)`, `hidePopover(part)`, `showModal(part)`, `closeDialog(part, returnValue)`, `send(part, input)` виджету, корень которого — эта часть, `watchKeys()` / `unwatchKeys()` для клавиш, нажатых где угодно на странице, `claimPointer()`, чтобы касание при перетаскивании не прокручивало страницу, а клик, которым оно заканчивается, поглощался, `scrub(part, ...)` / `stopScrub(part)` для одной приостановленной анимации, которую двигает перетаскивание, `flushStyles(part)`, который отвечает `browser.flushed`, `measure(request)`, который отвечает `measure.done`, `awaitAnimations(part)`, который отвечает `browser.animationEnd`, `animateHeight(part, open)`, `scrollTo(part, options)`, `setText(part, value, selection)` для текста, который поправила маска, `commitText(part, value)`, который ещё и отправляет `change`, как пикер, `commit(part)`, который отправляет `change` для уже показанного текста, `emit(name, value)` для колбэка `on<Name>` из options. Шаг никогда не трогает мир; таймер возвращается поступлением.
- **Вывод**: `shape.part(select, render)`: селектор перечисляет, что читает часть, рендер строит атрибуты из этого кортежа. Часть перерисовывается только когда меняется один из её входов, поэтому стрелка в сетке из 10 000 ячеек трогает две. Кроме атрибутов у части есть два канала, которые адаптер пишет сам: `props` для того, что может сказать только свойство элемента, например `indeterminate`, и `live` для значений, которые меняются каждый кадр, например смещение при перетаскивании.

Переиспользуемая логика — **фрагмент**: функция с сигнатурой шага, обобщённая по ключу и нужным полям, которая не знает о других фрагментах. `roving`, `selection` (single, multiple и range, в одном и в двух измерениях), `typeahead` и раскладка `grid` экспортируются из `@vega-ui/core`.

### Файлы

| Файл | Содержит | Никогда |
|---|---|---|
| `widgets/src/<component>/widget.ts` | Форму, шаги, части вывода и инварианты виджета в `defineWidget`; команды, которые он принимает; чистые селекторы для хуков, например `isSelected` | React, DOM, ссылки на элементы |
| `widgets/src/<component>/<name>.ts` | Чистые помощники одного виджета, которые сделали бы `widget.ts` длинным | Побочные эффекты |
| `Component.tsx` | `useWidget(widget, options, widgetEnvironment)` и контекст, который передаёт handle вниз | Логику: условие про клавиши, выделение или фокус принадлежит шагу |
| `components/*` | Части: `useOutput(handle, widget.output.part, key)` и `handle.merge(attrs, props)` или `handle.listen(attrs, props)` на корне | Эффекты, которые пишут принадлежащее виджету, `focus()`, `showPopover()` |
| `widgets/src/<component>/__tests__/widget.test.ts` | Node-тесты на `simulate` из `@vega-ui/core/test` со строгими инвариантами: пути пользователя как списки поступлений и ожидаемых снимков | DOM |
| `__tests__/*.browser.test.tsx` | Адаптер и разметку: что видит пользователь и слышит скринридер | То, что уже доказал node-тест |

Логика, общая для двух виджетов, живёт в `packages/widgets/src/<segment>`; контекст или хук живёт в компоненте-владельце, а другой компонент импортирует его только через `../Owner`, `../Owner/contexts` или `../Owner/hooks`, не глубже; общий React-код без владельца, например `createContext` и адаптер виджета, живёт в `packages/ui/src/internals/<segment>` и никогда не импортирует папки компонентов. Папки компонентов не импортируют друг друга по кругу. Это проверяют локальные правила ESLint (`eslint/components.mjs`).

### Правила

- **Браузер первый.** Что он сделал — окончательно: поповер, закрытый light dismiss, в следующем снимке `shown: false`, потому что адаптер это прочитал, и `aria-expanded` следует за этим, а не за `open` родителя. Значение родителя — команда, на которую виджет отвечает `showPopover` / `hidePopover` по `lifecycle.options`.
- **Пользователь первый.** Обработчики пользователя идут до обработчиков виджета; `event.preventDefault()` в них останавливает виджет, а клавиша, которую виджет обработал, доходит до обработчиков выше с `defaultPrevented`. Событие, которое браузер уже обработал, внутренний виджет потребил или портал доставил снаружи корня в DOM, пропускается.
- **Один механизм.** Состояние меняется только в шаге. Адаптер нормализует, доставляет, применяет вывод и исполняет действия; условий про виджеты в нём нет. Компонент никогда не пишет состояние из эффекта и не вызывает браузерное API сам.
- **Объявленные входы.** Шаг, который читает браузер, оборачивается в `listening(inputs, step)`. Адаптер слушает только события, которые дают объявленный вход, плюс фокус, доставляет клавишу, только если шаг объявил её или направление, в которое она превращается, а `simulate` отклоняет вход, который не объявил ни один шаг, так что тест в node не проходит на событии, которое страница никогда не доставит.
- **Виджет — это его корни.** Триггер и поповер в верхнем слое — два корня одного виджета (`setRoot(element, name)`, `handle.rootAt(name)`). Событие внутри любого из них принадлежит виджету, ключ и направление даёт ближайший корень, а фокус между ними не покидает виджет. Портал React по-прежнему принадлежит DOM: содержимое принадлежит виджету, потому что это его зарегистрированный корень, а не из-за дерева React.
- **Один владелец у каждого факта.** Указатель принадлежит адаптеру до отпускания; фокус — шагу через `act.focus`; порядок коллекции — данным (`cells`) или DOM-реестру, объявлено один раз.
- **Контролируемые значения.** Изменённое владеемое значение вызывает `onChangeX` один раз и держит новое значение до следующего `setOptions` с ответом родителя. React-адаптер синхронизирует опции во время рендера владельца и уведомляет подписчиков после коммита, поэтому части читают ответ родителя в том же проходе, а значение, которое родитель оставил, не доходит до DOM. Починка никогда не пишет контролируемое значение: ядро его восстанавливает, вывод фильтрует, `onRepair` сообщает.
- **Инварианты.** `check` и `repair` выполняются после каждого коммита. В тестах нарушение бросает исключение; в продакшене чинится и сообщается в хук диагностики пакета (`internals/widget`). Библиотека никогда не пишет в консоль.
- **Каждый кадр — мимо фреймворка.** Значение, которое меняется на каждом кадре, как сдвиг при перетаскивании, идёт в канал `live` своей части, а свойство без атрибута, как `indeterminate`, — в `props`. Оба пишет сам адаптер ядра, поэтому они не стоят рендера и одинаково работают под любым фреймворком; само движение — это CSS, который читает переменную. Атрибут, который запускает анимации, которых шаг ждёт через `act.awaitAnimations`, тоже идёт в `live`: фреймворк может отрисовать его уже после того, как адаптер прочитал анимации; если его должен отрисовать сервер, как `hidden` свёрнутой секции, он остаётся и в атрибутах.
- **Стоимость пропорциональна изменению.** Коллекция и раскладка мемоизированы по идентичности входов; селекторы — по снимку; реестр пересортировывается только когда зарегистрированный элемент добавлен, удалён или перемещён. Новые опции с тем же содержимым ничего не пересчитывают.
- **Читаемые имена.** Шаги принимают `(state, input)`; коллекция — `collection`, ключ — `key`, действие — `action`. Однобуквенных имён нет.

### Путь данных

- **Действие пользователя:** событие → адаптер строит поступление и читает значения браузера → шаги → один коммит → `onChangeX` один раз → подписчики → действия.
- **Новые пропсы:** рендер владельца передаёт опции виджету без уведомлений; layout-эффект уведомляет подписчиков и исполняет действия `lifecycle.options`.
- **Монтирование:** с `cells` как данными виджет знает элементы до их отрисовки, поэтому в серверном HTML правильный tab stop. Без них элементы регистрируются через `useItem`, и виджет получает их в порядке DOM сразу при изменении реестра, без рендера компонента. `lifecycle.connect` приходит, когда адаптер подключён и элементы зарегистрированы.
- **Композиция:** виджет на основе другого оборачивает его шаги, как пикеры периода на сетке; виджет, который управляет виджетом внутри себя, регистрирует его корень своей частью и посылает ему поступления через `act.send`, как `Calendar` фокусирует день своей сетки дней после выбора года; компонент посылает `command(name)` через `handle.send` только из своих обработчиков событий. Виджеты никогда не делят состояние.

### Как написать виджет

1. Прочитать паттерн [APG](https://www.w3.org/WAI/ARIA/apg/patterns/): части, их роли и атрибуты, каждую клавишу.
2. `state({...})`: чем виджет владеет, что внутреннее, чем владеет браузер, откуда коллекция.
3. Выбрать фрагменты: `roving`, `selection`, `typeahead`, `grid`.
4. Написать шаги паттерна, которые фрагменты не покрывают, каждый в несколько строк: `(state, input) => input.is(key.escape) ? handled(closed(state)) : undefined`.
5. Части вывода с их селекторами.
6. Инварианты: что должно выполняться в каждом снимке, с починкой.
7. Node-тесты на `simulate`: каждая клавиша паттерна как список поступлений.
8. Компонент: `useWidget`, `useOutput`, `useItem`, больше ничего.

Пример: [packages/widgets/src/select/widget.ts](../../packages/widgets/src/select/widget.ts).

## Истории, тесты и документация

Эти три слоя служат разным целям и должны оставаться согласованными:

- истории описывают реалистичное поддерживаемое использование и визуальные состояния
- тесты описывают поведение, взаимодействия и пограничные случаи
- документация описывает контракт для потребителя: когда использовать компонент, как его собрать и что обычно ломается

В этом репозитории истории в основном лежат рядом с компонентами в `packages/ui/src/**`, а конфигурация Storybook — в `.storybook/`.

## Источники истины документации

При документировании компонента придерживайтесь приоритетов:

1. исходный код — для публичных экспортов и формы типов
2. истории — для поддерживаемых примеров и вариантов
3. тесты — для пограничных случаев и гарантий поведения
4. CSS-модули — для точек настройки стилей и локальных переменных компонента

Так документация не уходит в паттерны, которые исходный код на самом деле не поддерживает.

Общее определение [источника истины](./glossary.md#источник-истины-source-of-truth) — в [глоссарии](./glossary.md#источник-истины-source-of-truth).
